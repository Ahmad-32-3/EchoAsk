Case study · a caching layer for LLM APIs

Two questions that mean opposite things can look 98.4% identical to a machine.

I built a caching layer that sits in front of an LLM and tries to answer one question honestly: when is it actually safe to reuse an old answer for a question someone asked a slightly different way? Reusing answers saves money, but reuse the wrong one and a user gets a confident answer to a question they never asked. This walkthrough follows what I tried, where it broke, and the fix that helped without fully solving it. Every number here comes from a script in the repo, including the security bug a fresh review caught before I called it done.

01

The setup

Every LLM-backed support bot gets the same shape of traffic. A small number of questions get asked constantly, each one worded a dozen different ways. “How do I reset my password” and “I forgot my password” are the same request in different clothes, and a cache that matches on the exact text will never notice.

Calling the model every time costs money and adds delay, so the goal is to remember answers and hand them back when the same question comes around again. The easy version matches the exact wording. The interesting version matches meaning: I turn each question into a set of numbers that stands in for what it's asking, then reuse an answer when a new question's numbers land close enough to an old one's.

That second version is where the risk lives. A cache that guesses wrong doesn't crash or throw an error. It quietly hands back a confident, wrong answer, and nothing downstream knows to complain.

So I built the whole thing around one made-up but realistic setup: a support bot for a subscription product, answering reworded versions of about 15 real questions (billing, refunds, plan changes, outages). Then I asked three things in order. Does plain exact-matching already get me most of the way? Where does meaning-matching break? And when it breaks, can a cheap fix rescue it?

02

Try 1: exact match only

baseline

Before touching meaning-matching at all, I checked what the dumbest possible cache buys me. Take the question, look up its exact text, hand back the stored answer if I've seen it word for word. No meaning involved, so there's no way for it to confuse two different questions.

94.0%

That result is easy to undersell. Real support traffic is lopsided: a few questions get asked far more than all the others, and a lot of them arrive as the exact same text (a “Cancel subscription” button, a canned FAQ link). Exact-matching catches almost all of the savings, and it physically cannot serve the wrong answer. Most of the win, none of the risk. That's the bar the next two sections have to beat.

03

Try 2: matching on meaning

where it breaks

Exact-matching misses every reworded question, which is the whole reason to want meaning-matching in the first place. The obvious next step: turn both questions into numbers, and count it a match when they land close enough. The only open question seemed to be how close is close enough. So my first experiment swept that setting across its full range and scored each value against 20,000 question pairs that real people had already labeled as same-question or not.

How accuracy shifts as I tighten the match line, across 20,000 labeled pairs
matches that are right real matches caught combined (reference)

Two things matter in that chart. When the cache calls two questions a match, how often is it actually right (the blue line)? And of all the real matches out there, how many does it manage to catch (the amber line)? A cache that's safe to ship needs the blue line high. It never gets there.

Nowhere in the range does the cache get more than 54% of its matches right. The best it reaches is 53.9%, and only by getting so strict that it catches barely a quarter of the real matches. Loosen it enough to be useful and it drops below 46% right: worse than a coin flip on whether a “match” is really the same question. I also tried bolting on a check for shared words, on the theory that overlapping vocabulary might rescue the close calls. It didn't move the ceiling.

It's worse on my own scenario than on the general benchmark. I hand-built ten pairs that look almost identical but mean things a support bot must never mix up:

04

Try 3: add a guard

the fix, and its limits

The wrong matches share a pattern. Every one above shares nearly all its words with its partner and differs in exactly the part that flips the answer: a number, a currency, a role, monthly versus annual, upgrade versus downgrade, a “not.” Catching that takes no understanding of meaning at all. It takes reading the sentence for the few words that change everything.

So I added a guard that runs after the meaning check, not instead of it. If two questions clear the match line but disagree on a number, or sit on opposite sides of a short list of watched groups (billing period, role, direction, currency, contact channel, time reference), or one says “not” where the other doesn't, the guard blocks the reuse and falls through to the next-best answer, or to an honest miss.

That's a genuine gain: five times fewer wrong answers on the exact set I built to break it. But it's a patch, not a proof. Two pairs still slip through, and both point at something the guard can't reach:

“Cancel my subscription?” vs. “Cancel and still get a refund?”. The second question quietly asks for more, and it needs a longer, different answer. No number, currency, or “not” gives the guard anything to catch.

By design, not a gap

A test (test_known_gap_not_caught_by_design) pins this exact pair down on purpose, so a later change to the guard can't quietly claim to cover something it still misses.

05

The real tradeoff

The sweep and the hand-built pairs are worst-case on purpose. The question that actually decides whether to ship this is what happens on normal, mixed traffic. So I ran 4,000 requests through three setups back to back: weighted so a few questions dominate the way they do in real life, spread across 15 questions, with four confusable pairs mixed in.

Cost tells a clean story. Exact-only cuts spend 94.0% against no cache, and adding the meaning tier pushes that to 99.2%. Read only that line and turning meaning-matching on looks like an easy call.

It isn't. The meaning tier adds 5.3 points of hit rate over exact-matching alone, and 18.9% of those extra hits serve the wrong answer. Of the 3,205 meaning-based hits in this run, 607 handed someone an answer to a question they didn't ask. Exact-matching alone already captured almost all of the savings with zero risk. The extra that meaning-matching buys is real, but it comes stapled to an error rate the cost number never hints at.

06

What still doesn't work

The meaning model is weak
The tool I used to turn questions into numbers is a basic one, not a modern sentence model. My build environment couldn't reach the download for the better one, so I substituted. That's a real step down, and a good chunk of the bad accuracy above is a property of this specific tool, not a law of meaning-matching in general. Swapping it (I explain how in the design section) is the first thing I'd do before trusting these numbers past a demo.
The guard will always have a next gap
The two misses in Try 3 aren't near-catches. They're two different shapes of failure the guard has no rule for. Any guard built from a fixed list of rules will always have a next category it hasn't been told about. It lowers the error rate; it doesn't reach zero.
It only looks at one question at a time
Every test here treats a question as a standalone line of text. A real conversation carries context: “what about for annual?” right after a monthly-refund question is perfectly clear to a person, and completely meaningless to the cache on its own. I haven't tested this, and it's probably a bigger real-world risk than anything I measured above.
07

The bug that almost shipped

process, not just numbers

Before I called this done, I ran the code past an independent review: fresh eyes, no stake in the result, told to hunt for correctness and security problems instead of confirming the story so far. It found one.

⚠ cross-tenant data leak · found live, fixed same day

Each customer's cached answers are supposed to be walled off from every other customer's. The lookup found a customer's entries by matching their name against the stored keys, and the matching language treats the * character as “match anything.” So a request that set its customer name to * matched every customer's data, not just its own. The reviewer proved it live: stored one customer's private answer, asked for it back under a different customer's wildcard name, and got it. That broke the one guarantee the whole project leads with.

I fixed it the same day instead of filing it for later. A customer name now has to be plain letters, numbers, dashes, and underscores, checked both at the front door and again inside the cache itself, so nothing with a wildcard in it ever reaches the matching step. Three tests reproduce the original exploit. I re-checked it live over real HTTP: the request that used to leak data now gets turned away at the door.

None of my tests had caught it, because none of them used a customer name with a wildcard in it. That surface was just never touched. It's the best argument I know for putting a real review in front of “done.” It caught the one bug that actually mattered, and nothing else would have.

08

Why these tools, and what I turned down

technical detail

This is the section where I get specific. Some of these calls were forced by my build environment and some I made freely, and I want to be clear about which is which. A few of the free ones went against the brief I started from, and I think they made the project better.

Storage: plain Redis and a brute-force scan, not a vector database

The instinct for meaning-matching is to reach for a dedicated vector database (Qdrant) or Redis Stack with its HNSW index, so lookups stay fast as the data grows. I used plain Redis and a simple loop that scores the new question against every stored one. That sounds naive until you count what actually gets stored. A cache like this holds one entry per distinct answer the system gives, not one per request. For a single service that's a few hundred to a few thousand entries, not millions, no matter how much traffic you throw at it. Scoring a new question against a few thousand stored vectors in NumPy takes well under a millisecond. An approximate-nearest-neighbour index like HNSW earns its extra moving parts once you're into tens of thousands of vectors and up. Below that, it's a second stateful service to run and reason about, solving a speed problem I don't have.

Plain Redis bought a safety property too. I keep each customer's entries under their own key prefix (sc:{customer}:*), so a lookup physically can't see another customer's keys. A single shared vector index would instead rely on every query remembering to filter by customer, and one forgotten filter is a silent cross-tenant leak. That's almost exactly the bug that bit me anyway (section 07), which is the best possible argument for making the isolation structural instead of a filter you have to remember.

Meaning model: spaCy word vectors, not a trained sentence model

My plan was fastembed with bge-small, a proper trained sentence model that's good at telling “worded alike” from “means the same.” My build environment couldn't reach the servers those weights download from, so I fell back to spaCy's en_core_web_md, whose word vectors ship inside the install package with nothing to fetch at runtime. I turned down two other options on their own merits: sentence-transformers would have dragged in PyTorch, a heavy dependency for something meant to sit in a fast request path; OpenAI's hosted embeddings are high quality but cost money per call, and part of the point was showing you can answer the core question without paying per embedding.

The tradeoff I accepted is real and it's the main limitation of the whole project. Averaging word vectors is worse than a trained sentence model at exactly the thing this study cares about: telling a real paraphrase apart from two sentences that look alike but mean different things. That weakness is a big part of the poor accuracy in the charts above. Outside a locked-down environment, swapping the single embed() function for bge-small or MiniLM is the whole upgrade. Nothing else in the design changes.

The model behind the cache: a deterministic stand-in, not a paid API

Every eval needs to be re-runnable at zero cost each time I change a setting, so on a cache miss the “model” is a deterministic stand-in paired with a cost calculator built on real published per-token prices. A real hosted model would make the benchmark slow, non-repeatable, and metered, none of which helps me answer the question I care about. I wired in a local Ollama model for a single genuine proof that the proxy really does call out on a miss, but my sandbox blocked that download too, so that one path is built and not yet run. The cost figures come from the price math, not from invented savings.

Test data: Quora Question Pairs, plus a hand-built adversarial set

To measure whether a “match” is actually correct, I need an answer key: pairs of questions humans have already labeled as the same or not. Quora Question Pairs is exactly that, hundreds of thousands of labeled pairs, free. It covers the general case. It doesn't cover the domain-specific traps a support bot hits (monthly versus annual, one order number versus another, USD versus EUR), so I hand-built ten of those myself. That's the set the guard was designed against.

Left out on purpose: a metrics dashboard

Prometheus and Grafana would give this real production monitoring. They also wouldn't change a single conclusion in this walkthrough, so they'd be scope without insight. I cut them to keep the project pointed at the one question it exists to answer.

09

Run it yourself

The proxy and Redis start with one command, and the model behind them defaults to the free, deterministic stand-in.

# start the proxy + Redis
docker compose up --build

# first time seeing this prompt — miss
curl -X POST localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"namespace":"demo","prompt":"how do I reset my password"}'
# cache_hit: false, cache_tier: null

# a paraphrase — semantic hit
curl -X POST localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"namespace":"demo","prompt":"I forgot my password, help"}'
# cache_hit: true, cache_tier: "semantic"
Reproduce the three evals
pip install -r requirements.txt -r requirements-eval.txt
python -m eval.download_qqp
python -m eval.threshold_sweep        # → threshold_sweep.csv / .png
python -m eval.adversarial_audit      # → adversarial_summary.txt
python -m eval.traffic_replay         # → traffic_replay_summary.txt
pytest tests/ -v                      # 20/20 — tiering, isolation, TTL, guard

This is a runnable project plus the notes I built it from. Every number above came from a script that still runs, and the loop/ directory in the repo keeps the full build log, including the parts that didn't work the first time.
